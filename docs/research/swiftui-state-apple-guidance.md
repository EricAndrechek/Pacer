# Apple's documented model of SwiftUI/SwiftData dependency tracking

Reference for auditing the `modalRoot` bug class: a page's `@State` was set from a `Button` action closure passed down through child views; the only *reader* was a custom `ViewModifier` on the page, reached via `@Binding`. The modal didn't appear until an unrelated update redrew the page (up to 45s). Making the page's own `body` read the `@State` directly fixed it. A minimal offscreen repro of the same shape did **not** reproduce it.

Tags: **[Apple]** verbatim from a developer.apple.com doc, WWDC transcript, or Swift Evolution proposal. **[Apple-eng]** an Apple/DTS engineer's on-the-record forum reply — real but not formal documentation. **[Community]** third-party, converging/credible but not Apple's word. **[Gap]** searched for, not found — flagged rather than guessed.

## 1. How SwiftUI decides a view must re-render

**[Apple, secondary transcript]** WWDC21 "Demystify SwiftUI" (10022): identity / lifetime / **dependency** are three separate concepts. "A dependency is just an input to the view" — `@Binding`, `@Environment`, `@State`, `@StateObject`, `@ObservedObject`, `@EnvironmentObject`. SwiftUI maintains a dependency graph and calls `body` only on views depending on a changed dependency. (Apple's transcript page is JS-rendered/unfetchable; corroborated by 3 independent note-takers with no disagreement.)

**[Apple, verbatim]** `documentation/swiftui/managing-model-data-in-your-app` — the precise, current rule: *"a view forms a dependency on an observable data model object... when the view's body property reads a property of the object. If body doesn't read any properties... the view doesn't track any dependencies."* Same rule restated on the **[Apple]** `State` doc for a `@State`-held `@Observable` object shared with a subview: updates fire "only when the subview's body reads the property."

**Declaring/holding a property is not enough — reading its value inside a tracked `body` is what creates the dependency edge.** This is the single most important sentence for the audit.

**Granularity differs by system [Community + Apple].** Combine-backed `@ObservedObject`/`@EnvironmentObject` invalidate the **whole view** on any `objectWillChange`, not per-property (WWDC20 "Data Essentials in SwiftUI", secondary). Apple's own **[Apple, verbatim]** migration doc (`migrating-from-the-observable-object-protocol-to-the-observable-macro`) confirms the consequence of mixing systems: *"a view updates only when an observable property changes and the view's body reads the property directly [for Observable]... In contrast, a view updates when any published property... changes, even if the view doesn't read the property, [for ObservableObject]."* → "updates too often" vs "doesn't update" bugs can look identical but have opposite root causes depending on which system the model behind them uses. Audit for stragglers still on `ObservableObject`.

**Mechanics of "a read" [Community, converging, not Apple's wording].** Chris Eidhof's "Attribute Graph in SwiftUI," objc.io Swift Talk S01E429, and saagarjha.com's reverse-engineering agree: the graph is **pull-based**. A write marks known dependents dirty; if nothing was ever recorded as a dependent, the write is a no-op for scheduling — the stale value only surfaces the next time *anything* re-runs a `body` that finally reads it. The dependency edge is created by the wrapper's `wrappedValue` **getter executing** inside a tracked pass — not by `update()`. **[Apple, verbatim]** `dynamicproperty/update()`: *"Updates the underlying value of the stored value"* / *"SwiftUI calls this function before rendering a view's body to ensure the view has the most recent value."* This is a **sync** step (wires live storage), documented separately from — and prior to — whatever records the dependency. **[Gap, Apple-acknowledged]** An unanswered Apple Forums thread (`forums/thread/773010`, Jan 2025) asks Apple to resolve exactly this ambiguity; no reply as of this research.

→ **This is the literal mechanism of the 45s delay:** if nobody's `body` ever executed `modalRoot`'s getter on the failing path, the write marked no dependent dirty. The next *unrelated* re-render that happened to run the page's `body` was the first chance for anything to read the now-current value — exactly "an unrelated update redrew the page" fixing it as a side effect.

**[Apple-eng, load-bearing]** Swift Forums (`swiftui-bindings-does-reading-them-in-body-mean-view-will-re-render/34600`) — Apple engineer **Joe Groff**, on record: *"Bindings ought to trigger updates the same as the thing they're bound to. We've filed a bug about the bad interaction with NavigationLink here"* (rdar://60594597). Confirms binding-driven propagation has **known, filed Apple bugs** in specific compositional shapes — there `NavigationLink`, here a `ViewModifier` reached via `@Binding`. A recognized *class* of SwiftUI bug, not a misunderstanding of `@Binding`'s contract.

**Reads inside stored/escaping closures [Apple, verbatim, best documented analog].** `managing-model-data-in-your-app`, on a `List` content closure: *"LibraryView doesn't form a dependency on... title because... body doesn't read it directly. The view stores the List content closure as an @escaping closure that SwiftUI calls when lazily creating list items... instead of LibraryView depending on a book's title, each Text item of the list depends on title."* A dependency belongs to whoever's `body` **actually executed a read**, wherever that physically happened — not wherever the closure was *declared*. Scoped to Observation explicitly; not restated for classic `@State`/`@Binding`, but the mechanism above is the same for both (community-bridged).

**Two separate invalidation mechanisms [Community, fatbobman.com]:** (a) **Parent-driven/structural** — a coarse "did the reconstructed view's stored inputs compare equal" check, decides if a child's body runs *as a consequence of the parent running*. (b) **Self-driven/dependency-graph** — a getter read during a view's own last body execution creates a direct edge, independent of the parent. Pacer's bug is consistent with the write only ever mattering via (a) — only when the page re-ran for an unrelated reason and reconstructed the `ModifiedContent` fresh — because (b) never got an edge. Reading `modalRoot` in the page created a (b)-edge, guaranteeing a scheduled re-run on write.

**[Gap, explicit]** No source addresses the *exact* composition: closure captured several levels down, invoked later, writing a `@State` declared above, read only by a `ViewModifier` via `@Binding`. Consistent with the minimal repro not reproducing it — the mechanism likely depends on a structural detail (node identity stability, exact tree position of the read, transaction timing) not captured by the general "must read" rule.

## 2. ViewModifier vs. View — is tracking the same?

**[Apple, thin — confirmed gap]** `documentation/swiftui/viewmodifier` gives only the mechanical shape (`func body(content:) -> Self.Body`) and says nothing about dependency-tracking scope or whether `body(content:)` gets an independent AttributeGraph node.

**[Community, unverified]** One WebSearch aggregate (untraceable to a specific article) claims a modifier's `body(content:)` gets its own independent tracking scope. Present as unverified, not established.

**[Structural inference, not a citation]** `ViewModifier` shares the same `DynamicProperty`-discovery machinery as `View` (a modifier can declare `@State`/`@Binding`/`@Environment`, `update()`-synced the same way) — supports that it *should* be capable of its own edges, but doesn't guarantee a given modifier's `body(content:)` actually read the value at top level, vs. only forwarding it further into something else that may or may not read it.

**[Apple, WWDC21, different question — don't conflate]** "Inert modifiers" (`.opacity(1)`) not changing structural identity is about identity churn (§3), not dependency recording.

**Audit rule (synthesis):** For every `ViewModifier`/`View` holding a `@Binding`/`@State`/`@Environment` used only to build content passed elsewhere (a stored closure, `.sheet`/`.overlay` content, a child init) — verify **some `body`/`body(content:)` in the chain actually reads the `wrappedValue`** at top level of a tracked evaluation, not just forwards it unevaluated. A read buried in a deeply nested/lazily-constructed closure is the shape most likely to silently fail to register.

## 3. View identity

Source for this section (verbatim quotes): **[Apple]** WWDC21 "Demystify SwiftUI" (10022), speakers Matt Ricketson, Luca Bernardi, Raj Ramamurthy; WWDC23 "Demystify SwiftUI performance" (10160) where noted.

**Explicit vs. structural identity:** *"explicit identity: using custom or data-driven identifiers"* (`.id()`, `ForEach` `id:`) vs *"structural identity: distinguishing views by their type and position in the view hierarchy."* SwiftUI views are value-type structs — no pointer identity — so identity must be explicit or structural. Structural identity is the **generic type** the `@ViewBuilder` result-builder produces: `if`/`else` compiles to `_ConditionalContent<True, False>` — each branch is a structurally distinct type even if branches look identical onscreen.

**Same identity → state persists; different identity → reset.** *"At the beginning of a view's identity... SwiftUI allocates storage for State and StateObject... Whenever the identity changes, the state is replaced."* / *"View values are ephemeral... but what you can control is their identity."* → `if isEditing { EditForm() } else { ReadOnlyForm() }` loses in-progress `@State` on every toggle — distinct identity, independent storage lifetime.

**Apple's explicit recommendation:** prefer one parameterized view over branching view types — *"try to preserve identity and provide more fluid transitions. This also helps preserve your view's lifetime and state."* Rewriting a single view as two branch-selected types "for clarity" silently changes animation (fade/replace vs. smooth transition) and resets state.

**`Group` does not fix branch-identity loss** — **[Apple]** the `Group` doc only claims layout-transparency, no identity claim. **[Community]** wrapping `if`/`else` in `Group` doesn't merge the `_ConditionalContent` split. Fix: move the condition inside a modifier's *argument*, not around the view.

**`AnyView` hides structure from diffing — avoid.** *"AnyView... hides the type of the view it is wrapping... SwiftUI can't see the conditional structure... In general, we recommend avoiding AnyViews whenever possible."* WWDC23 10160, on `List`/`Table`: conditional-view or `AnyView` row content *"results in list needing to build all the views to retrieve the row identifiers because it doesn't know how many views each element resolves to."* → `AnyView` in a `ForEach`/`List` row builder forces eager row construction, defeating on-demand/lazy creation that `fetchLimit`-scoped rollup views rely on. Fix: `@ViewBuilder` preserves the typed `_ConditionalContent` tree instead of erasing it.

**ViewModifier + identity — best single quote for this bug class**, Raj Ramamurthy: *"If the condition changes... we end up with a new identity because there is a branch here... branches are a form of structural identity... Note that the branch here is in a modifier... you might have branches like this across files without even being aware of it! ... everything we've discussed here applies to views and view modifiers."* Fix, with mechanism named ("inert modifiers"): *"An opacity of 1 has no effect... the framework can efficiently prune away the modifier... moving the condition inside the opacity modifier... Now when the condition changes, only the opacity needs to change."* Apple's own audit checklist: *"When you introduce a branch, pause for a second and consider whether you're representing multiple views or two states of the same view."*
```swift
// BAD — branch = two identities, state under `view` resets on toggle:
if isExpired { view.opacity(0.5) } else { view }
// GOOD — single identity, only the modifier's VALUE changes:
view.opacity(isExpired ? 0.5 : 1.0)
```

**[Community inference]** `ModifiedContent<Content, Modifier>` (behind `.modifier()`) is `@frozen`/`Equatable`/`Sendable`. By the identity mechanism above, a `.modifier()` chain becomes part of the diffed type at that tree position — but as long as the *sequence/types* of modifiers at a position don't change between updates, wrapped content's identity (and its `@State`) survives updates that only change modifier *argument values*. Apple's `ModifiedContent` doc never uses the word "identity" — synthesis, flagged. **[Gap]** whether a modifier's own internal `@State` persists/resets independently of its content's identity is unaddressed.

**`ForEach` identity [Apple, doc].** Requires `Identifiable` or explicit `id:`. **[Community, not Apple-documented]** using `enumerated()`/array index as id is a well-known pitfall (nilcoalescing.com; Forums thread 736409) — reorder/insert/delete reassigns each *position's* identity to different data, so per-row `@State` sticks to position instead of following data. No Apple source states this explicitly — community-only.

**`.equatable()`/`EquatableView` [Apple, verbatim, doc-only].** *"Prevents the view from updating its child view when its new value is the same as its old value."* **Zero hits** in either WWDC21 10022 or WWDC23 10160 transcripts — confirmed gap, explicitly checked. **[Community inference]** a body-reevaluation optimization layered on the normal pipeline, orthogonal to identity — skips computing a child's body if its new value `==` the old, rather than computing then diffing. → an auto-synthesized or hand-rolled `==` that ignores a closure/reference property causes silent staleness, easily misdiagnosed as an identity/dependency bug when it's a bad `Equatable` conformance.

**`switch` [Gap]** — no verbatim quote retrieved; by analogy to `if`/`else` the same rule should apply, but this is inference, not sourced.

## 4. `@Observable`

**SE-0395 "Observability" [Apple]** (Hausler & Cook; Implemented Swift 5.9). `withObservationTracking` is **one-shot, not a subscription**: *"Any access to a tracked property within the apply closure will flag the property; any change to a flagged property will trigger a call to the onChange closure."* Re-registration is the caller's job — SwiftUI's renderer re-wraps `body` in a fresh call every render for this reason. Access is instrumented at the **synthesized getter** via a shared `ObservationRegistrar` (`self.access(keyPath: \.order)`); properties marked `@ObservationIgnored` or read via reflection are invisible. "Accessed" means the getter **actually executed** inside the tracked closure — holding/passing a reference doesn't count; dependency propagates through nested computed-property getters too. `ObservationRegistrar` is documented thread-safe/`Sendable` — an internal-safety claim only, **not** a statement about SwiftUI rendering correctness under concurrent mutation (see below).

**WWDC23 "Discover Observation in SwiftUI" (10149) [Apple, verbatim] — the placement checklist, literally the audit checklist to use:** *"Does this model need to be state of the view itself? If so, use @State." "...part of the global environment? ...use @Environment." "...just need bindings? ...use @Bindable." "And if none of these... just use the model as a property of your view"* (plain `let`, no wrapper).

**Singletons read in body [Gap, confirmed].** Neither the session nor the migration doc mentions `static let shared`/global `@Observable` instances — not endorsed, not warned against; the 3-question checklist has no "singleton" branch. **[Community]** Swift Forums ("Swift 6 and singletons / @Observable and data races") — under Swift 6, a non-`Sendable` `@Observable` singleton triggers "Static property 'shared' is not concurrency-safe." Common fix: `@MainActor` the singleton.

**Background-thread mutation [Gap, Apple silent].** Neither SE-0395 nor the WWDC session states a MainActor requirement. **[Apple-eng, most authoritative available]** Philippe Hausler (SE-0395 co-author), Swift Forums: *"Observable itself does not provide any additional safety... but it is best practice to have models that are interacting with SwiftUI to be bound to the main actor."* **[Apple, corroborating, verbatim from declaration tokens]** `documentation/swiftui/view`: `@MainActor @preconcurrency protocol View` — *"A type conforming to this protocol inherits [@preconcurrency @MainActor] isolation... if the conformance is declared in its original declaration... Declare the conformance in an extension to opt-out."* So `body` is MainActor by default even though the `@Observable` model isn't required to be — mutating off-MainActor and a MainActor `body` reading it are, generally, two different isolation domains unless the model is pinned. → doesn't crash (registrar is internally thread-safe) but community reports describe rapid background mutations getting coalesced/dropped within a run-loop turn — silently missed renders. Safe pattern: `@MainActor`-isolate the model or hop via `Task { @MainActor in }`.

**`@Bindable` [Apple, doc].** `@dynamicMemberLookup @propertyWrapper struct Bindable<Value>` — bindings into an `Observable`'s mutable properties. Three shapes: property-level (`@Bindable var book: Book` passed in, for `$book.title`); local var inside body (`@Bindable var book = book`, e.g. in a loop); from `@Environment` (`@Bindable var book = book` after `@Environment(Book.self) var book`). A plain unwrapped property suffices for read-only/pass-down use; `@Bindable` is needed only once a `$`-projected `Binding<T>` must go to a child control.

**Partial migration — Apple explicitly sanctions it and documents the cost [Apple, verbatim].** *"You don't need to make a wholesale replacement... Your app can mix data model types that use different observation systems"* — immediately followed by the granularity-difference quote in §1. Also: `@StateObject`/`@ObservedObject`/`@EnvironmentObject` still compile against an already-`@Observable` type (compatibility) but **forfeit fine-grained tracking** — a silent perf regression, not a compile error, easy to miss since the code still "works." → grep for stragglers left on the old wrappers/protocol.

## 5. Anti-patterns Apple calls out

**"Modifying state during view update" runtime warning [Gap]** — no Apple doc/session names this exact string. **[Community]** Swift Forums (non-staff): *"it's an internal warning of the SwiftUI framework that notifies you that it doesn't support modifying parent views during a view update pass."* Fix (matches Apple's own patterns elsewhere): defer the mutation into `.onAppear`/`.task`/an action handler/`Task { @MainActor in }`, not synchronously inside `body`. → mutating `@State` (or an `@Observable` object read earlier in the same body) synchronously inside `body` triggers this and can flicker the UI — the mid-render trigger races the render already in progress.

**Reference types in `@State` mutated in place — silent-no-update trap [Apple, verbatim, directly on point].** `documentation/swiftui/state`: *"Use state as the single source of truth for a given value type..."* For `@Observable` objects: *"You can store observable objects created with the @Observable macro in State."* But for the **old** `ObservableObject` stored in `@State`: *"the view will only update when the reference to the object changes... The view will not update if any of the object's published properties change. ...use StateObject instead of State."* Also: *"You can safely mutate state properties from any thread"* — about the storage cell's setter being callable from any thread; don't conflate with `ObservationRegistrar`'s own thread-safety claim above. **[Apple, WWDC20 "Data Essentials in SwiftUI," corroborating, pre-Observation]** *"State is designed for transient UI state local to a view... This is when you should use ObservableObject"* [for model reference types] — origin of the `@State`=value / `@StateObject`=observable-reference split that `@Observable` later collapsed.

→ **Most worth auditing for:** storing a **plain, non-`@Observable` reference type** (an ordinary class) in `@State` and mutating a property in place produces **no view update at all** — change detection fires only on reassignment of the wrapped value for non-Observable types, not in-place mutation of an already-held reference. Compiles fine, looks reactive, silently isn't. Fix: make the type `@Observable`, or reassign a value type.

**Heavy work in `init`/`body` [Apple, verbatim].** WWDC23 10160: *"expensive Dynamic Property instantiation, such as allocating and initializing a state object... Another source is work done in body... It's important that body itself is as cheap as possible."* Worked fix: a `@State` model's slow synchronous `init()` becomes an empty `init()` plus `.task { await model.fetchDogs() }`. Update pipeline, documented: *"produce a new value for the view... update all of the dynamic properties... body runs to produce the view's children"* — `init` and `body` are both on the hot path of **every** dependency-triggered update, not called once per lifetime. Debug tool (with caveat): `Self._printChanges()` — *"never guaranteed to always exist... never submit a call to this method to the app store."* → maps directly to Pacer's own documented incident class (AGENTS.md Performance section): any `@State` default value/`init`/computed property doing file I/O or O(N) work in `body` re-runs on every scan/save tick.

## 6. SwiftData

**`@Query` re-fetch granularity — coarse, confirmed by Apple DTS [Apple, doc + Apple-eng].** `documentation/swiftdata/query`: `@MainActor @preconcurrency struct Query<Element, Result>` conforms to `DynamicProperty`, `Sendable` — **not `Observable`**; it's `@FetchRequest`-style, not built on Observation. **DTS Engineer Ziqiao Chen**, Forums thread 774561, on record: *"it is hard for SwiftData to determine if a change is really relevant to the result set... with reasonable performance, especially when object graph is complicated"* — confirming **any save to that context re-triggers every `@Query` view using it**, regardless of relevance; SwiftUI's own diffing (not `@Query`) is what's sometimes granular downstream. **[Community, secondary WWDC23 "Meet SwiftData" summary]** per-property change tracking on an *already-fetched* `@Model` instance is separate and Observation- flavored — mutating a held object's property can update a view without a full `@Query` re-fetch, but a *new* matching row or a delete needs `@Query`'s coarse path. → an `@Query` re-runs on **every** save anywhere in the app, not just its own predicate's rows; a high-frequency unrelated write (a scan cursor, tick metadata) can thrash every `@Query` view. This is the confirmed mechanism behind Pacer's own "one rate-limit write signal" rule (commit 03b9358) — SwiftData's actual documented-by-DTS behavior, not Pacer-specific.

**`FetchDescriptor` — `fetchLimit` real; `propertiesToFetch` likely a no-op [Apple doc + Community, doc-vs-observed mismatch, flag explicitly].** `@Query(FavoriteRecipesList.fetchDescriptor)` pattern, `fetchDescriptor` must be `static`/computed (init runs at view-init time). Apple's `propertiesToFetch` doc promises *"faster and more efficient fetches."* **[Community]** fatbobman.com, verified via Core Data's SQL debug flag (SwiftData's store *is* Core Data underneath): *"even with propertiesToFetch set, the generated SQL is still a SELECT that pulls every column... it does nothing at all"* — no faulting API exists in SwiftData at all. Corroborated by a second independent source. **[Gap]** `fetchLimit`'s effect on live-update semantics (vs. just row-count cap) is unaddressed. → the real perf lever is `fetchLimit` + predicate scoping + schema splitting, not `propertiesToFetch`.

**`ModelContext` — thread confinement, mainContext, autosave [Apple, doc + WWDC23 "Dive deeper into SwiftData" 10196, verbatim].** `ModelContext` is a `class`, **not `Sendable`** — confined to one actor. *"This context is bound to the main actor... The Query() macros use the same context."* / *"The main context is a special MainActor-aligned model context intended for working with ModelObjects in scenes and views."* `autosaveEnabled`: *"the context calls save() after you make changes... also at various times during the lifecycle of windows, scenes, views, and sheets."* Default `false` for hand-created contexts, `true` for `mainContext`. **[Gap]** no documented interval for "periodically save" — one unverified forum comment speculates ~10s; treat as folklore, not fact. `willSave`/`didSave` notifications are real but scoped **per-context** — not documented as a cross-context merge mechanism (no SwiftData equivalent of Core Data's `mergeChanges(fromContextDidSave:)`).

**`@ModelActor` [Apple, doc].** `@ModelActor()` *"Converts a Swift actor into a model actor by generating boilerplate... that fulfills the requirements"* — `modelContainer`, `modelContext` ("serializes any code running on the model actor"), `modelExecutor`. **[Gap]** no Apple guidance found on *when* to reach for it vs. a plain background `ModelContext`; not mentioned by name in the "Dive deeper" transcript retrieved.

**Cross-context propagation — the single most load-bearing SwiftData finding [Gap, extensively confirmed].** No Apple doc (`ModelContext`, `ModelActor`, `ModelContainer`, `Query`, or any WWDC transcript retrieved) states a mechanism by which a save in one `ModelContext` notifies/merges into another. **No documented SwiftData equivalent to Core Data's `mergeChanges(fromContextDidSave:)`.** Multi-year forum evidence of inconsistent, OS-version-and-platform-dependent behavior:
- Thread 734177: background `ModelActor` *inserts* didn't trigger `@Query` updates, but *deletes* did; filed FB12689036 (Jul '23); "fixed" then broke again (list corruption); still present iOS 17.3–17.4; regressed again iOS 18 beta 5 (FB14750050). No Apple reply.
- Thread 767081: background updates merge fine in iOS 18/18.1 *until* the main context also edits the same item once, then silently stop.
- Thread 762183: a fix landing in one iOS 18 beta didn't work in Simulator, only on device.
- Thread 731426: one poster's only reliable workaround was subscribing to Core Data's own `.NSManagedObjectContextDidSave` notification directly — bypassing SwiftData's API entirely.
- Thread 758882: *"I can only see my data if I quit and relaunch the app"* — reproduced iOS 17 and 18; workaround (author's own words, "less than ideal"): force-touch `@Query` results on `scenePhase == .active`.

**Treat this as unverifiable, not a yes/no fact** — "sometimes, inconsistently, OS-version-and-platform-dependent, no documented mechanism, no documented guarantee." → a background `@ModelActor` save is not reliably guaranteed to make a mainContext `@Query` observe the change promptly, or at all, without a relaunch or manual nudge. Pacer's own architecture (MainActor-confined `SamplePersister`/`ScanCoordinator`, bulk recomputers explicitly committing the main context first so its own fetches see in-flight inserts) already routes around this exact gray area rather than trusting automatic propagation — empirically justified, not overcautious.

## 7. Concurrency in views

**`.task(id:)` [Apple, verbatim].** `view/task(id:name:priority:file:line:_:)`: *"SwiftUI can automatically cancel the task after the view disappears... If the id value changes, SwiftUI cancels and restarts the task"* — tested via `Equatable`. Order of cancel-old vs. start-new is **not documented as guaranteed** — don't rely on the old task's cancellation handler having run before the new task's synchronous prefix executes. `name:`/`file:`/`line:` params are a documented **no-op prior to macOS 26.4** — inert for a macOS 15 target; classic semantics apply. **[Apple]** WWDC21 "Discover concurrency in SwiftUI" (10019) — correct session title (not "Meet async/await..."): *"A task's lifetime is tied to the view's lifetime... canceled when the view's lifetime ends."* → a reference-type `id` whose *properties* mutate but the instance stays `===`-stable never restarts the task if `Equatable` is identity-based; over-broad `id` causes spurious restarts; a `.task` attached too high in the hierarchy never restarts on navigation because its own view never tears down.

**`@MainActor` isolation of `View`/`body` [Apple, verbatim, from declaration tokens].** `documentation/swiftui/view`: `@MainActor @preconcurrency protocol View` — *"inherits [@MainActor] isolation... if the conformance is declared in its original declaration... Declare the conformance in an extension to opt-out."* → adopting `View` via an **extension** silently loses `@MainActor` inference, no warning. **[Apple, WWDC24 "Migrate your app to Swift 6" (10169), verbatim, dates the SDK change]**: *"this includes the SwiftUI View protocol... you might be able to remove some of those [now-redundant] main actor annotations."* This SDK-level annotation shipped with **iOS 18/Xcode 16 (2024)**, independent of language mode.

**Dating correction — SE-0466 is a separate, later mechanism.** `SWIFT_DEFAULT_ACTOR_ISOLATION` (SE-0466, "Implemented Swift 6.2") is **WWDC 2025/Xcode 26, not 2024** — module-wide default isolation for every *unannotated* declaration, vs. the `View`-only SDK annotation above which shipped a year earlier. Commonly conflated. Seeing this build setting doesn't explain `View.body`'s MainActor safety (already SDK-guaranteed); it explains why a *plain non-View class* compiles without explicit `@MainActor`. **[Apple, historical context]** SE-0401 (Implemented Swift
5.9) removed a prior rule where a View's isolation was inferred from
*which property wrapper* it used — largely moot for `View` post-2024 SDK, still relevant for plain `@Observable`/view-model classes not conforming to `View`.

**`Task.detached` [Apple, verbatim].** `swift/task/detached(name:priority:operation:)`: *"Don't use a detached unstructured task if it's possible to model the operation using structured concurrency... Child tasks inherit the parent task's priority and task-local storage... You need to handle these considerations manually with a detached task."* **[Apple, WWDC21 "Explore structured concurrency in Swift" (10134), verbatim, the actor-specific claim]**: *"A directly constructed task still inherits the actor, if any, of its launched context"* vs. detached tasks *"aren't constrained to the same actor and don't have to run at the same priority as where they were launched."* → `Task.detached { try? modelContext.save() }` inside a view action, capturing a MainActor-created `ModelContext`, runs with **no actor affinity** — not guaranteed to observe the context from its creation isolation domain; since `ModelContext` isn't thread-safe (§6), this is a real data-race risk. **[Gap]** no exact Apple quote combining "use `@ModelActor` instead of `Task.detached`" — inference from the two documented facts above, not a located direct statement.

**Off-MainActor mutation of tracked state [Gap — inference from well-established, widely-corroborated Swift 6 behavior, not one Apple quote].** Under Swift 6, mutating a `@MainActor`-isolated property from a non-isolated context is a compile error (representative diagnostic: `Main actor-isolated property 'x' can not be mutated from a non-isolated context; this is an error in Swift 6`). Under Swift 5 mode with minimal checking, the same code compiles silently and races — visible only via Thread Sanitizer or an intermittent "Publishing changes from background threads" warning. Both `.task(id:)`'s and `Task.detached`'s closures are typed `@isolated(any)` — isolation is inferred at the call site. A `Task { updateSomeObservable() }` written directly in a `View`'s body infers `@MainActor` and is safe/correctly diagnosed; extracting that same closure into a `nonisolated` helper (or handing it to `Task.detached`) breaks the inference chain silently in pre-Swift-6 contexts. → the exact class of "invisible until profiled/sanitized" bug Pacer's own AGENTS.md documents catching only via real runs — extracting a closure out of a `View`'s tracked-MainActor context into a detached/nonisolated helper is a common refactor that silently drops the isolation guarantee.
