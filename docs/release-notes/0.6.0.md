The dashboard comes back where you left it, and an agent in a fan-out stops gating on somebody else's rate limit.

## Heads up if your agents use the pacing skill

`--model auto` has changed what it does when a session is running **more than
one model at once** — an orchestrator with a fan-out of subagents under it.

It used to answer with the model on the session's newest turn. That turns out
to be unsound: a subagent does not get its own session id. Claude Code records
its turns under the *parent's*, and nothing in the environment names a
per-agent model, so "which model am I?" is genuinely unanswerable from inside a
subagent. In practice a Sonnet builder was told it was running Fable and gated
itself on a weekly cap at 95% that did not bind it and would not reset for
three days — stalling the whole run on somebody else's limit.

So it no longer guesses. With one model in flight, nothing changes: `auto` is
exact, as before. With several, it binds only the account-wide windows (5-hour,
weekly) and says so:

```
pace: GO — 5h 12%, 7d 32% (cap 85%). [model ambiguous (claude-fable-5-1,
claude-sonnet-5) — account-wide windows only; pass --model to gate on yours]
```

**If you orchestrate subagents, pass `--model` explicitly** — the orchestrator
picked the model, so it is the one part of the system that knows. The skill's
paste-into-every-subagent clause has been updated to say so. The trade is
deliberate but it is a trade: an orchestrator running `auto` mid-fan-out is no
longer stopped by its own per-model cap.

`--model auto` also *says* what it resolved now, on the `GO`, `PAUSE` and
`report` lines. It always decided something; it just never told you, which is
why the wrong answer went unnoticed.

Scraping the API? `/v1/session` gained a `models` array — every model the
session has run recently, newest first. Additive; `model` still means what it
did.

## The window stays where you put it

Park the dashboard on whichever display and Space suits you and it comes back
there — across relaunches, across updates, and across a monitor that was still
asleep when you logged in.

That was the bug that started this release: installing an update put the window
back on the wrong display at the wrong size. Four separate things were
overwriting the position you had chosen, including the app's own restore
recording its own moves as if you had made them.

Three behaviours changed with it:

- **Summoning the dashboard takes you to it.** Clicking the menu bar used to
  drag the window onto whichever display your cursor was on, and onto whichever
  Space you happened to be looking at. Now the window stays where it lives and
  macOS switches you to it. If your Mission Control settings won't follow it,
  Pacer brings the window over instead, so a menu-bar click never does nothing.
- **A dashboard you closed stays closed.** Pacer meant to do this and never
  did — a closed window came back on the next launch regardless. Logging in
  should not put a window on screen you deliberately shut.
- **A monitor that is asleep at login no longer costs you the position.** The
  window waits rather than being dumped somewhere arbitrary, and returns home
  when that display does.

## Why this is 0.6.0 and not 0.5.2

Pacer's convention is that a minor bump means a SwiftData reset. **This release
does not reset anything** — your history is untouched and no migration runs.

It is a minor because the behaviour contracts changed: `--model auto` answers a
different question in a fan-out, and the dashboard's window handling is
meaningfully different from what you are used to. That seemed worth a number
people would notice.
